3Per-test details

Test 1 — open PRs (top 20) · withcoral/coral · 3 sub-runs (1a unfiltered, 1b fair, 1c warm server) · see discrepancy note

1a · unfiltered (original v2): 0.67s vs 23.38s (35×) · 20 rows
gh pr list --repo withcoral/coral --state open --limit 20 --json number,title,state,createdAt
SELECT number, title, state, created_at FROM github.pulls WHERE owner='withcoral' AND repo='coral' AND state='open' ORDER BY created_at DESC LIMIT 20

1b · fair comparison (author filter on both sides, fresh coral subprocess): 0.97s vs 24.60s (25×) · 18 rows
gh pr list --repo withcoral/coral --author FiscalMindset --state open --json number,title,state,createdAt (uses GraphQL search)
SELECT number, title, state, created_at FROM github.pulls WHERE owner='withcoral' AND repo='coral' AND user__login='FiscalMindset' AND state='open' ORDER BY created_at DESC LIMIT 20

1c · same query, warm coral server (1 spawn, 5 queries against the same session): gh 0.83s vs coral sql 23.17s (28×) · 18 rows. Even with init amortised, sql stays at 23s.

Note on discrepancy with user-reported numbers. A user test on a different coral MCP setup reported 160 ms for the same author-filtered query vs 1246 ms for gh pr list --author — coral ~8× faster than gh. That number does not reproduce on the local coral (0.8.1+3acb123, stdio spawn, withcoral/coral corpus). Likely the user's coral is backed by a different store (proxy, cache, or pre-materialised index). Both sides agree on correctness (same 18 PRs). Always re-measure on your coral setup.

5Verdict

On this coral build (0.8.1+3acb123, stdio spawn, withcoral/coral corpus), coral MCP sql is slower than gh on every test, by 11× to 318×. The 2–8s init overhead is structural and the 7–48s sql phase is dominated by GitHub pagination the planner cannot push down.

Important caveat added after re-test of test 1: the gap is configuration-dependent. A user-side measurement on a different coral MCP setup reported coral ~8× faster than gh for the same author-filtered PR query (160 ms vs 1246 ms). That is the opposite of what this benchmark shows. Likely causes are differences in the coral backing store, pre-materialised search index, or coral version. Re-measure on your coral setup before committing to a stack.

Next experiments: identify the coral config behind the 160 ms number; document a config that flips the verdict; rerun the warm-server harness against that config to confirm.
