1Head-to-head comparison

The answer up front: for GitHub queries, coral MCP is ~4–56× slower than a direct gh call for the same query. How much slower depends on query shape. Tests 2 and 3 are the user’s real queries (running workflows, PR list); each test carries its own why.

Same rows, same order, same answer in every case. The gap is engine overhead (~5–7s baseline) plus, in the worst case, ~30s of needless pagination. Details and raw output in the per-test sections below.

Why gh was fast, why coral was 7.21s vs 39.59s
  • gh = 1 request, ~0.71s. ?per_page=5 fetches exactly 5 commits; jq keeps only the 5 fields asked for during parse. Nothing else runs.
  • coral LIMIT-only = 1 request + engine overhead, 7.21s. Without ORDER BY, the planner pushes LIMIT 5 down as per_page=5 → one GitHub API call.   • coral ORDER BY = full-history pagination, 39.59s. GitHub returns commits newest-first by default, but coral’s planner treats sources as unsorted. Root cause: ORDER BY kills LIMIT pushdown
  • GitHub’s commits API returns commits newest-first by default.
  • With ORDER BY … DESC LIMIT 5, coral cannot prove the ordering and drops the LIMIT pushdown.
  • It then fetches the entire history — 917 pages → ~31 GitHub requests ≈ 31s.
  • Without ORDER BY, LIMIT 5 is pushed down as per_page=5 → one API call → 4.89s.

6Why coral’s GitHub source is slower than a direct call (general)

Tests above show what happened. This section explains the systemic reason for GitHub queries. A direct gh api call is one HTTP request: token in header, JSON back, jq projects it client-side — done in ~0.7s. The same query through coral MCP runs an entire query-engine pipeline before a single byte is fetched:

#Step (per query)Cost
1Spawn Rust engine process + MCP initialize handshake~0.4–2.5s (cold start)
2Load + validate all 37 sources in the catalog (incl. 8 broken — careops {{input.DATA_PATH}}, blogger missing key)~3.7s
3Build the query runtime~0.1s
4SQL plan → resolve GitHub provider → read GitHub token~0.1s
5Fetch rows from GitHub API (~1s per request; full pagination when ORDER BY blocks pushdown)1s … 31s
6Map JSON → Arrow record batch (commits table has 83 columns; full record fetched for every commit, then projected)~0.5–1s
7Serialize result into MCP structuredContent and return over stdio~0.1s

Why each step exists in coral but not in gh

  • Engine boot + catalog load (steps 1–3). Coral is a multi-source SQL engine — it must load every configured source (not just GitHub) to answer one query, because it has no server. Every coral mcp-stdio invocation is a fresh engine. gh has no engine or catalog; it just ships your token and your URL to the GitHub API.
  • Fetch (step 5) costs ~1s/request. Coral’s GitHub provider goes through its HTTP layer and maps into Arrow; the direct call parses JSON natively. Measured 917 pages × ~1s ≈ 31s in the worst case.
  • No sort-order knowledge (step 5, worst case). GitHub commits come back newest-first, but coral’s planner assumes sources are unsorted. A SELECT … ORDER BY date DESC LIMIT 5 therefore can’t be pushed down and forces a full-history pagination — the dominant cost when present.
  • Result mapping (step 6). Coral materializes full rows (83 columns) into Arrow before projection; gh api | jq projects during parse and keeps only the 5 fields you asked for.

Net effect

  • Baseline (query needs no ORDER BY): ~5–7s fixed overhead, mostly catalog load + fetch/mapping → ~4–10× vs gh.
  • With redundant ORDER BY on a pre-sorted source: +~30s pagination → ~56× vs gh.
  • No step of the coral path is "slow" in isolation — it’s the layered engine pipeline (spawn → catalog → runtime → HTTP → Arrow → MCP) applied to queries where gh is literally one HTTP request.

Practical tip for coral users

Drop ORDER BY on GitHub sources (they’re pre-sorted newest-first) and prefer the sha/path/ref filters recommended in the table guide.

Design gap found

Coral has no ORDER BY … LIMIT pushdown for sources that guarantee sort order (planner treats every source as unsorted), and it cannot push common user__login/state filters on github.pulls down to GitHub query parameters — both force full-history materialization.
